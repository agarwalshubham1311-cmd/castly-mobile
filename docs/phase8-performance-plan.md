# Performance plan — owner review required

No million-user capacity or load-test success is claimed. M8.3 will measure the approved integrated system using k6 against disposable/staging targets with an explicit hostname allowlist and no production credentials. Scenarios: login/JWKS verification, talent search/profile, booking create/transition, two-way messages, favourites, entitlement reads, outbox claim/receipts, admin directory/search and aggregate analytics. Use synthetic populations and realistic concurrent users; registered user count alone is not throughput evidence.

Proposed SLO candidates, not release gates until approved: p95 discovery/profile ≤500 ms, p95 authorized writes ≤800 ms, HTTP error rate <1% excluding expected 4xx, queue p95 age <60 s when approved providers are healthy. Define peak request rates, region, dataset, worker concurrency and provider limits before acceptance. Record p50/p95/p99, throughput/errors, memory/CPU, Hikari saturation, PG buffers/slow queries/EXPLAIN ANALYZE, lock waits, queue lag and worker throughput. Baseline→sustained→peak→spike→soak→failure/recovery, with a fixed seed, warmup and run identifiers. No claims of before/after gains without measurements.

M7.1 reads are bounded keyset pages (max50) with PK indexes. Actor advisory locks serialize security-sensitive operations; benchmark audit insertion/permission checks and role-revocation contention before increasing admin concurrency. M7.4 must use indexed/preaggregated tables/materialized views with documented refresh/freshness and consented provenance. Introduce cache/Redis/queues only for measured bottlenecks; never cache stale permissions across revocation or invalidate RLS isolation.
