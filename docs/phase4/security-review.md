# Phase 4 security review

Local implementation review, 2026-11-10. No independent penetration test or hosted validation was performed.

Authorization is enforced by Spring JWT authentication, transaction-local `private.request_user_id()`, restricted `castly_api` grants, database RLS and write guards. Reviewer scope rows under `trust_private.reviewers` start empty and require owner provisioning. The Auth directory, transaction identity and TLS handling are inherited without privileged bypass. New functions use `SECURITY INVOKER`; no service-role credential is used in business requests. Tests include cross-account reads/writes, client metadata escalation, forged badges, review and dispute eligibility, conflicts, SQL injection input, RLS and concurrent transitions.

Verification badges require a current approved revision of reviewed profile/portfolio facts. Editable Auth metadata never establishes confirmed email or phone. The MVP does not request government IDs, biometrics or identity matching. Portfolio references use existing private asset authorization; reviewer access is limited to active requests with a bounded review window.

Booking reviews require both participants' explicit completion attestation. Public ratings count only visible eligible reviews. Blocking is symmetric for initiating new bookings/messages; pair locks serialize races. Existing participant records and cancellation paths remain available. Reports carry private reporter identity and are rate limited; identical incident retries dedupe while materially different incidents can be filed. Subjects see only controlled action/appeal information. Moderator/appeal decisions exclude interested parties and prior reviewers. Public trust indicators omit raw report counts, sensitive traits, numerical safety scores and automatic bans.

Text disputes require actual booking participation and `dispute-text-v1` consent. Image evidence is separately gated by a disabled flag, an empty-by-default approved policy table and a matching policy-version consent. The filter bounds upload request bodies before JSON/base64 parsing, including chunked requests; processing has a two-slot bulkhead. Only JPEG/PNG inputs are accepted, with dimension/pixel and output-byte caps; in-memory re-encoding strips image metadata. The private Storage bucket has caller-JWT policies for exact owner/dispute/object paths. Upload authorization serializes with deletion and expires after a five-minute lease. A preemptively inserted image row cannot be finalized by the backend. Signed URLs require an authorized `READY` record and expire within the evidence deadline and 60 seconds; a URL already issued cannot be instantly revoked. Evidence deletion is two-step with retry after Storage failure. Expired objects require a separately provisioned retention reviewer and Storage deletion; metadata-only expiry does not delete bytes.

Residual release risks: real Supabase Storage behavior and its RLS policy evaluation need staging tests with actual user JWTs; native Expo Go/Android flows, screen readers and hosted Realtime need device/environment checks. Operators must approve a concrete privacy notice, retention period, consent wording, deletion/appeal procedure and reviewer staffing before image acceptance. Reviewers can see private case material while a case is pending; retention operators can access expired objects solely to remove them, which must be disclosed and audited. Case text, audit and dispute retention/deletion policy also need approval before production activation. No real identities, documents or credentials were processed locally.
