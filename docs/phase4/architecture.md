# Phase 4 architecture

Phase 4 starts at stable `b86deb4`, which includes reviewed Phase 3 PR #5. The isolated `feat/phase4-trust-verification-safety` worktree contains six forward-only migrations. All new flags default false. The existing booking, messaging, Auth, subscription and notification boundaries remain in place; Phase 4 does not require the pending hosted notification migrations.

| Area | Authoritative source and behavior |
| --- | --- |
| Verification | A creator submits a statement and references existing portfolio items. An owner-provisioned verification reviewer records decisions and expiry. The badge is tied to reviewed profile/portfolio facts and their current revision. Trusted email/phone visibility reads only top-level Supabase Auth `/auth/v1/user` confirmation fields. No government ID or biometric collection is offered. |
| Completion and reviews | Both real booking participants must separately confirm an accepted booking before it becomes completed. Date passage and imported completed labels alone do not grant review eligibility. One review per participant/booking/target; public aggregates use only eligible, visible reviews. |
| Safety | Pair locks serialize block, booking creation and new message sends. Blocks are symmetric for new contact. Participants retain existing history and cancellation access. Report incidents are distinct by description and retry-safe for identical content; reviewer decisions and appeals are audited and require independent reviewers. |
| Trust | Public profile facts show verified status, attested completions and booking-based review totals. Private versioned triage snapshots use confirmed active moderation findings only. A bounded asynchronous refresh queue coalesces invalidations; stale private reads compare current authoritative counts. No public numerical score, raw report count or automatic sanction. |
| Disputes | Each participant may file one text case per real booking, add notes, track status and appeal a resolution within 30 days. Owner-provisioned dispute reviewers cannot decide their own case or its appeal. Cases exclude escrow, refunds and booking payments. |
| Image evidence | Optional JPEG/PNG input is bounded, sanitized in memory and re-encoded as PNG. Upload requires separate explicit consent to an owner-approved immutable policy version, private Storage bucket and caller-JWT RLS. Object paths bind owner, dispute and evidence ID. Access is short-lived, audited and deadline-bound. Deletion enters `DELETING` and becomes `DELETED` only after Storage removal; failed deletion remains retryable. |

The API runs as restricted `castly_api` with transaction-scoped identity. `trust_private` scopes are owner-provisioned; user metadata cannot grant staff access. Storage uses the caller's JWT and a publishable/anon project key. No service-role, BYPASSRLS, privileged business connection or SECURITY DEFINER helper is added. The verification application is profile/portfolio review, not identity-document proof.

API routes are under `/api/v1`: `/verification` and `/admin/verification`; booking `/completion` and `/reviews`, talent `/reviews`, `/admin/reviews`; `/reports`, `/blocks`, `/safety/actions` and `/admin/moderation`; `/trust/me` and `/admin/trust/{id}`; `/disputes`, `/disputes/{id}/notes`, `/disputes/{id}/appeal`, `/admin/disputes`, and `/disputes/{id}/images` plus authorized evidence URL/deletion/retention endpoints. All admin routes require the relevant database scope. List endpoints are bounded to 25 records per page. The Safety Center surfaces guidelines, reporting, blocking and dispute navigation with loading/empty/error states.
