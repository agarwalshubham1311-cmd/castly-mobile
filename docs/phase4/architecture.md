# Phase 4 architecture and dependencies

Baseline inspected: stable development b86deb4 (already merged Phase 3 PR #5 at 9bf180e). Phase 4 uses its own worktree/branch and never changes the parallel Phase 3 branch. Prior reconciliation inventory documentation is available, but actual hosted constraints/ACLs remain unverified; hosted owner inventory is a release gate, not a claim of inspection of live schema.

Verification is manual profile/portfolio review, not biometric or government-ID identity proof. MVP applications contain a statement and references to the creator's existing portfolio. Explicit `profile-review-v1` consent allows authorized reviewers to inspect those submitted objects. The badge means the profile/portfolio was reviewed and expires under a configurable policy; it does not guarantee safety. Trusted email/phone confirmation comes only from top-level Supabase Auth `/user` response fields; editable metadata is ignored. Unavailable provider data remains unknown.

New `trust_private` capability tables/functions are independent of Phase 3 subscription admins. The existing `private` namespace and Auth directory ACLs remain unchanged. Runtime uses only castly_api; reviewer scopes are owner-provisioned and self-readable, never user-writable. New helper execution is narrowly granted for authorized Storage policies. All functions use SECURITY INVOKER.

Planned completion flow: each actual participant explicitly confirms completion; only both confirmations permit accepted → completed. No date-triggered completion. Completed booking conversation access remains available; cancellation/history semantics are preserved. Reviews require that genuinely completed booking and target the other participant. Rating summaries count only visible eligible reviews.

Blocking uses symmetric pair locks at database write boundaries so racing block/create/send operations serialize. Historical participant SELECT/Realtime delivery stays intact; private moderation/evidence tables are not added to Realtime. Public trust consists of explainable indicators, never a numeric safety score or confidential violation evidence. No protected traits, opaque auto-ban, escrow, refunds or booking payment guarantee is introduced.

Sensitive evidence uploads remain disabled unless an operator explicitly approves/configures a privacy policy version, retention period and storage integration. MVP dispute text and existing booking references work without documents. Any enabled image attachment pipeline must sanitize/re-encode bounded images, require consent, reserve exact owner/purpose paths, enforce Storage RLS and expiry, and issue short-lived access only after API authorization. Government IDs/biometrics are prohibited by policy; no automatic identity matching is implemented.
