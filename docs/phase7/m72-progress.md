POST `/users/verifications/{id}/evidence/{evidence}/preview` additionally requires recent MFA and returns `{url,expires_in}`. It locks the application row, validates the current non-deleted portfolio reference under the existing privacy window, requests Storage with the current reviewer JWT, rechecks roster/evidence after the HTTP wait, and appends `portfolio.preview_issued` to the existing trust audit before returning. A failed authorization or audit never returns the capability. It uses only the `portfolio` bucket and configured trusted Auth project origin; no private-media/identity-document route exists.

Gateway controls: no redirects, complete-response 64KiB bound and five-second deadline using the existing Phase 6 bounded-body utility, canonical source paths, exact returned origin/path/query, expiration parsing bounded to 60 seconds and the original 30-day review window, publishable/anon key only, no service-role fallback, and sanitized errors. Supabase Auth access/refresh and admin-session tokens stay HttpOnly; the issued Storage URL is an intentional short-lived capability for the authorized reviewer. Already-issued URLs can remain valid until that bounded expiry; already-viewed bytes cannot be revoked. Storage enforces its signature on use; local expiry parsing does not purport to validate a Storage JWT signature independently. No URL/token is written to source audit or application logs. Production MFA/Storage/clock/cache behavior still requires approved staging verification.

Allowed decisions remain UNDER_REVIEW/VERIFIED/REJECTED/REVOKED; unsupported transitions still fail. There is no new SUPER_ADMIN issuance, reviewer enrollment, entitlement grant, booking mutation or general SQL proxy. Ordinary users, invalid/stale/other-user sessions, permission-only reviewers and roster-only support users cannot authorize these operations.

Directory pages use READ COMMITTED keyset semantics: concurrent name/state changes can change filter membership; refresh restarts pagination. There is no snapshot/export claim. Effective verification follows expiration and matching reviewed profile facts; projected digests store no raw verification statement. The source remains the existing Phase 4 review, not a new verification authority.

## Forward migration review

First new migration: `supabase/migrations/20261125100000_admin_user_read_models.sql`.

SHA-256: `00004c0adb5bdb18678ba0a431855d900a08e06bbc1bb69c51ad62ec20a457c4`.

Creates six minimized operational projections and one append-only history table in `admin_private`, all with RLS. Source-maintenance functions are SECURITY INVOKER with pinned pg_catalog search_path and qualified application names; PUBLIC/anon/authenticated/castly_api direct function execution is revoked. Maintenance grants are limited to the required columns, with no primary-key UPDATE grant. Direct mutations require source-trigger context; RLS and a depth guard reject fabrication. History exposes no application UPDATE/DELETE/TRUNCATE grant. Database owners remain trusted and can alter schema; application append-only controls do not defeat a malicious owner.

No SELECT/UPDATE policy on original users, bookings, messages, subscriptions, documents or storage is widened. The worker gets no admin schema access. No auth-schema access, SECURITY DEFINER, BYPASSRLS, service-role or authenticated membership is introduced. Actual source mutations and read-model/history maintenance commit or roll back together; direct database admin edits are not a supported application path.

The migration installs source triggers, backfills current metadata, and builds indexes in one transaction. It does **not** invent historical account events or activate administrators/reviewers/flags. At large cardinality, source locks, backfill volume, WAL/storage and index-building time require isolated restore rehearsal and an approved maintenance plan. No million-user capacity or online-lock SLO is established by synthetic fixtures.
