## Contracts and delivery sequence

M6.1 adds explicit Expo permission/device registration, owner token rotation/removal, generic payloads and authenticated opaque-ID resolution. An AFTER notification trigger derives per-channel/device outbox rows in the business transaction, deduped by event, recipient, channel and device. Trigger-only grants cannot be used for arbitrary cross-user writes. A separate non-owner/no-BYPASSRLS worker connection has only delivery-related metadata/contact access. The API connection remains castly_api. Both worker and providers default off; no migrations or network sends run automatically. Push uses Expo's HTTPS API only after separate approval. Tickets are not delivery receipts. Ambiguous dispatch/crash is quarantined, not blindly resent: Expo has no exactly-once remote-send primitive. Safe rejected attempts retry with bounded exponential backoff, then dead-letter; invalid tokens are deactivated. This favors no duplicate sends over guaranteed delivery.

M6.2 adds owner preferences, trusted verified-email synchronization, generic Lavender-branded transactional/optional templates, a disabled default provider and an optional Resend HTTPS adapter. API keys stay server-only; optional mail has HMAC unsubscribe capabilities and suppression. Signed delivery webhooks are verified before any state change. All Castly booking/account email is consented transactional; mandatory Supabase Auth security mail stays with Auth and is not repurposed as marketing. Optional digests/reminders/re-engagement require additional opt-in. No live send or paid activation occurs in this task.

M6.3 adds structured saved searches (no raw campaign prose), ownership/RLS, timezone/quiet hours, daily frequency limits, deterministic event keys and scheduling against current published/unblocked Phase 5 sources. Reminder sources are participant-visible requested/accepted bookings; accepted/completed message rules remain authoritative. Delete/export and opt-out are authenticated and actor scoped. Recipients' consent and targets are rechecked at dispatch. New user preferences default off. Schedules use explicit instants and local-day keys; no random re-engagement or sensitive-trait inference.

M6.4 records server-authoritative daily deduped funnel stages and delivery/open events only when analytics consent is present. No raw IDs, queries, PII, bodies, trust/evidence/payment records in event rows: actor keys use server HMAC, never a client tracking ID. Admin enrollment is owner-only. Aggregate endpoints enforce admin authorization and suppress cells under five actors. Document activation/cohort/window definitions and 90-day event retention; opt-out/delete erases the actor's retained events. No third-party analytics provider.
