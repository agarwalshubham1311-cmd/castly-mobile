# Phase 6 contracts and privacy definitions

All authenticated routes use `/api/v1/engagement`, existing Supabase JWT verification, Spring business APIs and transaction-local castly_api identity. No direct mobile business writes were added. Disabled mutations return 503; ownership failures are generic 404/403. Tokens, email bodies and receipt contents are never logged or returned to another actor.

- `GET /configuration`: independent push/email/engagement/analytics and actual delivery capability flags. Defaults false; worker/provider configuration is also required for delivery.
- `GET|PUT /preferences`: timezone, quiet_start/end (0–23; equal disables quiet hours), push_bookings/messages, email_transactional/optional, reminders, saved_alerts, reengagement, analytics. GET returns off defaults without creating records, including after deletion. Explicit PUT creates preferences; registration requires a saved push opt-in and is fenced against concurrent privacy deletion. PUT never accepts user_id/revision. Analytics opt-out deletes the user's retained event rows. Re-engagement activity tracking only operates for that opt-in.
- `POST /devices`: `{device_key:<installation UUID>,token:<Expo token>,platform:"android"|"ios"}`. Returns registration metadata, never the token. `DELETE /devices/{device_key}` is owner scoped. Max ten registrations; rotation of the existing installation remains possible at the cap. Registrations lease for 24 hours and renew on a consented app session/resume. A token registered to another live session returns 409; logout attempts revocation before signing out. Expired-token reclamation is constrained to possession of that exact token. Offline logout cannot immediately revoke a server registration: generic payloads, 24-hour expiry and authenticated resolution limit exposure; do not claim stronger native guarantees without testing.
- `POST /email/verify`: no email input. The verified mailbox is obtained from Supabase `/auth/v1/user`, matching the actor and confirmation timestamp, with a publishable/anon key. It is a notification-contact enrollment snapshot, valid for delivery for up to 90 days, not a security-mail identity authority. Re-sync/delete if the Auth address changes; an automatic Auth-change revocation feed is not installed. Confirm this enrollment model before production. Mandatory Auth security mail remains Supabase's responsibility; all Castly booking/account mail requires transactional opt-in. Preference changes are the implemented account-activity event.
- `POST /saved-searches/{id}/results` replays the owned structured search through Phase 5 in the chosen timezone and returns a bounded first page of current public matches. Other owners receive generic 404.
- `GET|POST /saved-searches`, `PUT|DELETE /saved-searches/{id}`: max 20 owned searches. Body `{label,filters:{category,city,region,skills,max_rate,days_ahead,window_days,include_unknown},alerts}`; relative dates 0–30 days ahead, 1–7-day window. Region must be creator shared; dated unknown availability needs explicit choice. Criteria use Phase 5's published/blocked/consent-aware read path. Digests additionally require the saved-alert preference and an opted-in channel. Disabled Phase 5 advanced search skips digests while independent reminders remain available.
- `POST /open/{opaque_delivery_id}`: authorizes the current recipient and booking/conversation via RLS before returning one fixed internal route. Payload-supplied URLs are never trusted. No guest navigation to private data. Open analytics require analytics consent and, for optional events, current channel/kind consent; old optional email opens after unsubscribe do not track.
- `GET /export`, `DELETE /data`: own preferences, registration metadata (no raw token), contact enrollment, saved searches, bounded delivery/schedule history and own event stages. Delete removes Phase 6 opt-ins/data, not the account/bookings/messages. Suppression hashes remain purpose-limited to prevent repeat bounce/complaint sends; owner retention policy must approve that exception.
- `GET /admin/analytics`: owner-provisioned `engagement_private.analytics_admins` only. No API self-enrollment or worker grant. Anonymous output suppresses cells under five actors and includes no subject keys, contact data or private trust records.

Public callbacks: `GET /unsubscribe/{signed_capability}` is a confirmation form, never an opt-out side effect. POST implements confirmation/RFC8058 one-click and disables optional email/reminders/digests/re-engagement, leaving separate transactional/Auth settings alone. The capability is delivery-bound HMAC, expires after 30 days, and cannot authorize account/booking access. No worker control connection returns 503 rather than pretending to unsubscribe. `POST /webhooks/email` requires valid Svix HMAC headers, ±300-second timestamp and at most 64 KiB. Duplicate webhook IDs are ignored. Signed bounce/complaint creates address-hash suppression; delivery acceptance is not delivery evidence. Keep the control connection and signing secrets available while send workers are paused.

## Event authority and dispatch

Existing notification insert guards and unique business-event keys remain authoritative. Their AFTER trigger creates one job per recipient/event/channel/device in the same transaction. Rollbacks produce no jobs. Ordinary API SQL cannot insert jobs directly or call enqueue outside a source trigger. Self-schedules validate participant/source/consent and canonical local-day keys. Worker role has no booking mutation, message-body access, auth schema access, privileged membership or RLS bypass. Metadata/device/contact reads are restricted to delivery sources; it cannot enumerate unused devices or grant admins/entitlements.

States: queued → sending (committed lease) → ticket → delivered, or queued/backoff, suppressed, dead, uncertain. Multiple workers use row locks/SKIP LOCKED. Recipient consent locks and the existing block-pair advisory lock serialize dispatch with opt-out/block acknowledgement. Known rejection can retry up to ten attempts; ambiguous acceptance/crash is uncertain and never automatically resent. Expo tickets need a successful receipt; email acceptance needs a signed delivery webhook. These indicate provider handoff, not that a person read a notification. No provider can guarantee exactly-once remote delivery. No client retry endpoint resets uncertain/dead jobs.

## Analytics definitions

Server-authoritative stages: successful search (legacy discovery, advanced/matching), public profile read, inserted save, booking request, Talent acceptance, participant message, and mutually completed booking transition. One `(HMAC actor, UTC day, stage)` row deduplicates retries/repeated actions. Activation is the first consented core action in retained history (or accepted onboarding), not a retroactive claim about pre-consent behavior. Notification delivered/opened events follow receipt/authenticated-open evidence and current consent. Stored subject keys are pseudonymous; only aggregate responses are anonymous. No pixel tracking, third-party analytics, queries, bodies, device tokens or trust/evidence/payment facts enter events.

Daily stage volumes are unique consenting actors, not a claimed same-person conversion rate: clients request and talent accept, and completion is attributed to the participant finalizing the transition. Weekly retention uses UTC Monday cohorts based on first observed activity within the rolling 90-day window; retained means observed again in the stated week. It is not lifetime signup retention or causal campaign attribution. Daily dashboards show the last 28 days; cohort cells require at least five retained actors and five cohort members. Worker maintenance deletes events older than 90 days and delivery/source/webhook/budget metadata older than 30 days. During a pause, keep an approved retention maintenance procedure; disabling the worker also stops its purge schedule. Preserve HMAC keys for deletion/export until retention completes.

Phase 6 JSON endpoints and complete provider responses are bounded to 64 KiB. Complete provider exchanges have a four-second deadline (including stalled bodies), trusted contact lookup five seconds. Consent and privacy deletion share a consistent preference-row lock order with registration, analytics and callbacks. Do not log full unsubscribe capability paths or request/response bodies in ingress/application debug logs.
