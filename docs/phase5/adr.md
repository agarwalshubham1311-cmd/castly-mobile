# ADR: Phase 5 discovery and matching

Status: implementation contract, 2026-11-11. Baseline is stable `b86deb4`; Phase 4 is unapproved and read-only. Issue #6 (saved here with source digest) is authoritative.

The server owns search, matching and generated suggestions. Advanced search reads only published talent profiles, public category/rate/skills and opt-in region; the existing public city stays at city granularity. No GPS or precise location is accepted. A new explicit creator day calendar is the only positive date availability source. An accepted booking blocks that date. Missing calendar data displays `unknown`; an explicit unavailable day, globally unavailable profile or accepted-booking conflict displays generic `unavailable` only for an already declared day; accepted booking conflicts are checked internally and never identified to searchers. An unaccepted request is not treated as a conflict. Availability filters include only dates explicitly marked available throughout the requested 1–31 day window and with no accepted booking conflict. The response never exposes whether a specific day has a private booking. Search is bounded to 25–50 rows/page, offset <= 10000, with indexed category/rate, region and calendar lookups. Existing `/talents` behavior remains unchanged while the new flag is false.

Campaign text parsing is a deterministic, strict local aid. It may infer known category, city, budget, date and explicit skills/deliverables/format; every inferred field is returned unconfirmed. The client must edit/confirm structured constraints and whether INR budget is an indicative per-day ceiling or a total campaign amount before matching. Invalid/protected-attribute targeting is rejected. Hard category, required skills, per-day rate ceiling, location and confirmed date availability filters run before soft ranking. Unknown dates enter only by explicit client choice and remain marked for direct confirmation; an undeclared booked day and undeclared free day have the same `unknown` response. Soft score uses sourced category/skill overlap, price fit, declared availability and a boolean match to a requested deliverable in a creator-supplied public portfolio label; no follower count, popularity, subscription tier, protected traits or inferred identity. Unknown data is shown and cannot be scored as a positive fact. Ties use stable public ID ordering. A shortlist has at most 20 candidates and per-candidate sourced explanations.

Personalization consent and external AI-processing consent are separate per-request, user-scoped booleans. Both default false and can be withdrawn by toggling off before the next request. No external provider is configured, paid for or called. The `SuggestionProvider` interface accepts only pseudonymous structured booleans/taxonomy IDs and validated numeric ranges, never names, UUIDs, URLs, contact details, bio/portfolio prose, messages, dispute/verification evidence, purchase tokens or raw prompts. A disabled provider yields deterministic local results. Future provider output may only reorder already authorized candidates within hard constraints, and must pass a strict response schema; it cannot add candidates, claim missing facts, invoke tools or persist. The current branch does not send data externally.

No campaign text, shortlist, AI output or personalization consent is automatically persisted. Returned draft briefs/profile suggestions/shortlist comparisons are labeled suggestions and editable in memory. Submitting a booking or profile edit remains the existing deliberate user action. Logging records route, duration bucket, count and anonymous failure code only. Bounded request size, rate limit and one-second local computation target keep cost at zero; future provider integration requires a separate privacy, retention/deletion, spend and latency approval. No sensitive trait inference is allowed.

One forward-only migration after hosted Phase 3 version `20261111052157` adds owner-managed availability days and opt-in public region, with RLS and restricted column grants. No Phase 4 object is referenced. The host requires owner read-only catalog/source inventory, exact SQL review and isolated-copy rehearsal before applying it. Feature flags remain off until reviewed deployment; disable each flag to roll back behavior without dropping creator calendar data.
