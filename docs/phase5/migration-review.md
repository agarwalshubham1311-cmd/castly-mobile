The migration creates owner-managed broad-region consent and day declarations, a trigger-maintained accepted-booking conflict aggregate, and actor-scoped rate counters. RLS is enabled on all four tables; anon/authenticated direct access is revoked. `castly_api` uses existing transaction-private request identity. The aggregate is readable only during its maintenance trigger, by the owner, or for a published creator on a specifically declared available day. API callers cannot forge aggregate writes or access another unpublished creator's rows. The API never returns the aggregate, its count, booking identifiers or private dates. A creator may delete their own day declaration; accepted booking conflicts remain authoritative. The normalized-skill partial GIN index is usable under a forced-plan disposable fixture EXPLAIN. That proves index compatibility, not production planner choice or latency.

Rollback is flag disablement, not destructive table deletion. Existing day declarations and region consent remain owner-managed until an approved data-retention/deletion policy and migration are reviewed. Provider output is not persisted. Operational rate counters are time-window state; an owner should set a retention/purge schedule before activation. Any production application of SQL, flag activation or data purge requires a separate approval.
